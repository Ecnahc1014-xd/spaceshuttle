## 工作特征

- 决策风格: [observed] 倾向先消除架构耦合，再进入大规模 3D 开发（出现次数: 1）
- 代码偏好: [observed] 重视渲染与逻辑职责边界和可替换性（出现次数: 2）
- 反馈偏好: [observed] 会直接指出玩法辨识度或技能手感不足，并提供明确目标数值与触发要求（出现次数: 2）
- 工作习惯: [observed] 希望将 2D 玩法表现逐步升级为 3D 体素/载具表现，同时保留既有规则与技能契约；引擎体素物理解锁后倾向先接到现有分层上、探测失败必须回退，而不是推倒规则层；Preview 上会直接指出体素路径的可见性/碎块比例问题（出现次数: 4）
- 性能关注: [observed] 会优先指出严重卡顿、节点泄漏和渲染批次问题，要求先解决性能再继续视觉迭代（出现次数: 1）
- 载具表现偏好: [observed] 运输车辆必须是可拖拽、可飞行、可碰撞的实际发射主体，不能只是底部装饰发射台（出现次数: 2）
- 审美倾向: [observed] 明确偏好正交投影但要求足够斜俯视以表现厚度；载具必须是大运式平头高顶、长货厢、三轴六轮重卡，并通过更浅的独立侧围区分侧面；不接受跑车/皮卡轮廓、方块瓦片车辆、缺色或静态空背景（出现次数: 4）
- 完整度要求: [observed] 不接受只有文字占位或“有功能但无空间反馈”的半成品；四弹药槽要具备完整状态信息，敌船撞线要有相机、材质、冲击波和警示反馈；敌机必须由真实独立方块构成，破坏后对应方块可见缺失，不能用完整模型掩盖规则砖块状态；战斗底部中央要能看见下一波敌人小图（出现次数: 3）
- 参考图使用偏好: [observed] 倾向直接提供游戏截图/飞机参考图，要求从参考中的低像素飞机轮廓采样出网格，而不是沿用旧主题轮廓或仅做风格换色；会点名 8bit 太空飞机大战，要求剪影可辨、同波成阵而不是随机散点（出现次数: 2）
- 运动与判定一致性: [observed] 要求载具转向具备可见过渡动画，并要求视觉模型外轮廓不得超出权威碰撞判定范围；也会直接指出拖拽操作位置、车辆模型投影中心与权威弹珠位置、预测轨迹折返点和体素拓扑之间的错位，偏好通过受控游戏态截图而非只看公式验证（出现次数: 3）
- UI 审美与验收标准: [observed] 不接受只有功能和技术文字的粗糙 UI；会直接根据实机截图要求结构级重构。dark-tech 骨架可留，但文案必须给正常玩家看：中文优先，禁止驾驶舱英文黑话（FLIGHT CONTROL/SESSION SEALED 等）。要求信息层级、主视觉、卡片可见性、触摸命中和战斗态 3D 可见性同时成立（出现次数: 8）
- 稳定性红线: [observed] 对“UI 消失 / 游戏卡死 / 输入无响应”零容忍，优先级高于视觉打磨；初始化链中任何可选资源缺失都不应导致整个后端启动失败，瞬时飞散对象必须有同屏数量预算；验收要求覆盖长时间真实战斗而非仅菜单截图（出现次数: 1）
- 边界与编队空间语义: [observed] 对“规则边界 ≠ 视觉边界”敏感：要求顶部反弹边在屏幕可见区之外（载具飞出画面才反弹），左右边对齐视觉；并会发现不同波次飞机仍可能重叠，要求生成与移动全程按完整 AABB 严格分离、不能只检查当批次（出现次数: 1）
- UI 打磨偏好: [observed] 在功能跑通后会要求 UI 大修：卡片要有完整可读的详情描述（不是短标签）、自动换行、稀有度/层数/风险等层级信息；倾向去除外部图片依赖改程序化绘制，布局更舒适、信息密度适中；会用实机截图直接圈出标题异常折行、字号过小、点击区与视觉不符等细节问题，验收以截图可读为准（出现次数: 2）
- 防线结算语义: [observed] 对越线扣血有明确规则要求：按“每行方块”独立碎裂并各自结算 0.5 血向上取整，升级加成只作用在整体合计后的数字而非逐块乘，要求碎裂反馈与权威扣血严格一致（出现次数: 1）
- 变现路径: [observed] 明确单机只做广告变现、不做内购；会先去开发者后台签广告协议，再要求接入激励视频与云存档（出现次数: 1）
- 节奏与数值手感: [observed] 会直接指出“刷怪过快、经验曲线不合理”，要求刷怪间隔/同屏密度与升级阈值一起调，偏好前几分钟有喘息、升级平滑而非连升；调整边界这类参数时要求用明确的数学方式（如两次取值的平均值）落地；对刷怪位置与进场动效敏感，要求新敌人整机从屏外平滑进入、不能在屏内凭空出现或突然横向回撤；多次放慢仍会被嫌快（9.5→11→14→18s 基础间隔），同时会抱怨首波入场太慢，间隔与下落速度必须分开调；验收偏好实机体感而非公式（出现次数: 3）
- 3D 箱体验收标准: [observed] 不接受只挂纹理名或只有薄体素的假箱体；要求敌方块有明显厚度、纹理、斜视可见侧面，命中后必须从主体前侧脱离并多轴旋转、飞散、缩放淡出；会直接指出“部分情况下碰撞/碎裂特效丢失”，且修完仍会复测漏检，要求规则层打最近格、挖空失败必须重试对齐网格；验收以运行态截图为准，不能只凭 build 或事件链存在宣布完成（出现次数: 4）
- 交互与表现取舍: [observed] 明确不要预瞄线和弹珠尾迹，优先车辆体量、敌方方块材质、命中后取消碰撞并旋转飞散、飞机之间不重叠；同时要求 UI 不消失且蓝紫主题统一（出现次数: 1）
- 操作手感: [observed] 对输入限制和等待空窗敏感：不接受只能在底部小区域起手拖拽（偏好全屏任意位置起手、手指不遮挡主体的相对拖拽）。重要教训（v0.10.15→17 召回反复）：不要在用户只反馈“空窗/不好用”时自作主张发明新机制（主动召回、预约发射等）——球本来就会自然回落补弹，新增召回被判定“多余”且引出误触吞输出、射不出去等连环问题，两版后被整体回滚；应优先做最小修正（回收点提前、修回收判定 bug、加快自然回落），提出新机制前先和用户确认。新操作要有视觉反馈确认（出现次数: 3）
- 验收方式: [observed] 会在真机/预览实机操作后直接反馈“射不出去”“UI问题明显”，要求同时定位规则 bug 与 UI 排版；修复后以探针+截图双重验证（出现次数: 1）

## 观察笔记

- [observed] 用户在正式 3D 开发前主动要求分离渲染和逻辑，说明对长期可维护性有明确要求；体素物理新功能也按“探测接入 + 规则零侵入 + 失败回退”落地（出现次数: 2）。
- [observed] 用户认为只改变基础参数不算有特点，更偏好拥有独立触发条件与战术用途的技能（出现次数: 1）。
- [observed] 用户偏好有持续压力与成长的肉鸽幸存者结构：要求基地生命高（100）、敌人编队推进且单块越线独立扣血、XP/升级三选一与局内强化，并要求明确削弱过强的加速技能；把"质量/设计度 1:1 超过组合参考"作为交付标准（出现次数: 1）。
